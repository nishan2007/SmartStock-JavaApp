# Store LAN receiving app

In Status, select **Receiving Inventory Web App…**, directly below **Mobile Item Web App…**. Start the shared server if needed and select **New Activation QR**. This QR opens Receiving directly and activates the browser. Receiving staff can issue a QR; starting/stopping remains restricted to device managers on the server. Both entries use the same LAN server and stopping it stops both apps. Alternatively, open `/receiving.html` on the Mobile Item Web App HTTPS address (port 8444). Start the existing server through Status → Mobile Item Web App, activate the browser with the register QR, then sign in. A Receiving link is available on the mobile home page.

The responsive page supports inventory products, custom inventory items and variants, typed or keyboard-scanner barcodes (leading zeros preserved), a delivery batch, confirmation, receiving slip number, and history filters. Receiving requires RECEIVING_INVENTORY; history additionally requires VIEW_RECEIVING_HISTORY. All authorization is enforced on the server using the session's store. No browser database credentials or new schema are needed.

A scan or search with one match opens the item automatically. Choose a result if there are multiple matches. Use the gallery arrows or thumbnails to review photos, then enter the delivered quantity and add the item to the batch. On tablets the batch updates beside the gallery. On phones the batch summary appears below the quantity controls. Open a batch row to edit its quantity or remove it.

Employees who also have EDIT_ITEM can use **Add photos** to take or choose photos for the selected item. Uploads append to the item’s gallery and save independently of the delivery batch. **Add Barcode** accepts a scan or typed barcode for the selected item and uses the same primary or additional barcode rules as desktop receiving.

Delivery quantities add to existing stock. Count corrections and loss adjustments remain in the supervised register workflow. If stock changes between search and posting, the entire transaction is rejected and staff must rebuild the batch with current stock. An uncertain connection result retains the identical body and idempotency key for safe retry; do not create another batch until the result is resolved. Drafts live only in tab memory.

The page and API use the existing LAN-only HTTPS server, activated-browser cookies, employee sessions, CSRF validation, transaction and idempotency storage. Public and forwarded peers are rejected by the existing local peer policy. No cloud route or public deployment was added. Keep ports 8444/8445 restricted to the trusted store network in the firewall; do not expose them through forwarding, VPN access for outsiders, or a reverse proxy. A private peer address alone does not identify a particular Wi-Fi network.

Validation: `node --test SmartStock/test/web/receiving.test.cjs`, `mvn -q -f SmartStock/pom.xml test`, and `git diff --check`. Before live use, verify the installed Java server, trusted HTTPS hostname, pairing/revocation, role changes, real PostgreSQL receiving and history, simultaneous sale/receipt behavior, store Wi-Fi access and blocked external access, mobile layout, and physical scanner. Source changes do not install into a live store.
